# 開発計画

> 企画概要で合意した進め方（①MVP → ②本気の最小ステージ → ③量産）を、作業と完了条件に落としたもの。

---

## 1. 全体の段階

| 段階 | 内容 | 次へ進む条件 |
|------|------|-------------|
| ⓪ 企画・設計 | 企画概要 → **詳細設計（本書を含む `docs/design/`）** → Codex への発注書 | ユーザーが詳細設計を確認し、MVP 着手の了承が出ている |
| ① MVP | 仮の見た目で、遊びの骨格と技術の流れを一通り動かす | 下記 3 章の完了条件 |
| ② 本気の最小ステージ | 第1章を製品品質で作る | 下記 4 章の完了条件 |
| ③ 量産 | 第2章以降を 1 章ずつ作る | 各章の完了条件（5 章） |
| ④ 仕上げ | 調整、クリア後要素、販売用ビルド | 6 章 |

Codex への発注は、開発と並行して**常に一歩先**を進める。

```
⓪ ──── ① MVP ─────────── ② 本気ステージ ──── ③ 量産（章ごと）──── ④ 仕上げ
 └ W0 発注 ─ 選定 ─ W1 発注 ─ W2 発注 ─┘  └ W3（第2章分）─ W4（第3章分）─ …
```

## 2. 役割分担

| 担当 | 役割 |
|------|------|
| ユーザー | 方向性の判断、Codex への発注と納品物の確認、試遊と手触りの感想、販売面の判断（ストア、商標の最終判断） |
| Claude | 設計、プログラム、3D モデル・アニメーション・地形（Blender スクリプト）、音、UI の実装、テスト、発注書の作成、納品物の 3D 化 |
| Codex | 絵（設定画、顔アイコン、UI の見た目、エフェクトの見本） |

## 3. ① MVP

**目的**：本気ステージに入る前に、「遊びの骨格」と「制作の流れ」が成り立つことを確かめる。見た目は仮（単純な形）でよい。

### 3.1 作るもの
| 分類 | 内容 |
|------|------|
| 土台 | Vite＋TypeScript＋Three.js＋Rapier の構成、60Hz 固定刻みのループ、sim と view の分離 |
| 操作 | ゲームパッドとキーボード＋マウス、操作の割り当て |
| カメラ | 3 人称の追従、壁の回避、ロックオン時の画面の収め方 |
| 移動 | 走る、ジャンプ（高さ調整、着地の猶予）、ダッシュ（無敵時間）、ダッシュジャンプ |
| 戦闘 | ロックオン（対象の選び方、切り替え、周回移動）、主武器（ラピッド型・チャージ型）、光刃（3 段コンボ、踏み込み斬り、溜め斬り）、特殊武器 1 種（ブレイクドリル）、ダメージと怯み、ヒットストップ |
| 敵 | 歩哨型と突撃型。状態機械の AI、攻撃の順番待ち、予兆 |
| 地形 | `30_レベルデザイン設計.md` 5 章の仮の地形（段差と溝の計測場、通路、戦闘の部屋、ひび割れた壁） |
| 物語の仕組み | 会話ウィンドウ（仮の顔アイコン）、イベントの台本 1 本、フラグ |
| HUD | HP、特殊武器、ロックオンの照準、セル |
| セーブ | セーブとロード（フラグ、位置、所持品） |
| 制作の流れの実証 | **Blender スクリプトで作った仮の人型キャラクター**（骨入り、待機・走り・ジャンプ・射撃・斬りのアニメーション）をプレイヤーとして動かす。Python のシンセで作った効果音と BGM を 1 つずつ鳴らす |
| デバッグ | 調整パネル（「YAML としてコピー」つき）、入力の記録、当たり判定の表示、性能の表示 |
| テスト | 単体テスト、手触りの数値テスト、ブラウザでの起動と撮影、GitHub Actions |
| 届け方 | 試遊版の届け方を決めて、実際にユーザーが遊べる状態にする（`40_技術設計.md` 10 章） |

### 3.2 完了条件
- [ ] ユーザーがブラウザで、仮の地形を 5〜10 分遊べる（移動 → 戦闘 → ドリルで壁を壊す → 宝箱 → 会話 → セーブ）。
- [ ] 調整パネルで手触りの数値をいじれ、その値を Claude に渡せる。
- [ ] 手触りの数値テストとブラウザでの確認が、自動で通っている。
- [ ] Blender → ゲーム → 撮影 の流れで、モデルとアニメーションが表示されている。
- [ ] ユーザーの PC で 60fps が出ている（仮の見た目で）。
- [ ] ユーザーから手触りの第 1 回の感想をもらい、反映している。

## 4. ② 本気の最小ステージ（第1章）

**目的**：製品版の第1章そのものを作る。**ここで作り方と品質の基準を固め、以降の量産はこの型に沿う。**

### 4.1 始める前にそろっていること
- Codex の W1（主要キャラ）と W2（第1章の素材）が納品され、ユーザーと Claude の確認が済んでいる。
- MVP の感想が反映されている。

### 4.2 作るもの
`30_レベルデザイン設計.md` の 4 章（第1章の詳細設計）のすべて。主なもの：

| 分類 | 内容 |
|------|------|
| 物語 | オープニング、見習いの仕事、ニコの救出、オルドの停止、父の銃、フレームとの適合、ボス、再始動、翌朝、章末の引き |
| 場所 | オルド背町（本気ステージの範囲）、背中の遺構 B1〜B4（20 部屋） |
| キャラクター | ハル（普段着・フレーム装着）、ナゴミ、ヤーナ、トルーデ、バートン、ニコ、店主、汎用の住人、黎明機構の飛行艇の中の影（ダグとハイナルの後ろ姿） |
| 敵 | 子番機、歩哨型、突撃型、盾型、浮遊型、ボス「閂」 |
| システム | ロックオン戦闘の全要素、チャージ化チップ、ブレイクドリル、工房（強化・開発）、雑貨屋、ギルドの依頼 2 件、ライフコア、遺物、セーブビーコン、近道、ドリルでの再訪 |
| 演出 | 会話（本番の顔アイコン、しゃべり音）、イベントシーン、フレームの装着演出、オルドの再始動 |
| 音 | BGM：タイトル、町（昼・夜）、遺構、ボス、イベント。効果音一式 |
| UI | 本番のデザインの HUD、会話、ポーズメニュー、工房、店、タイトル、設定 |

### 4.3 完了条件
- [ ] 第1章を最初から最後まで、約 90 分で遊べる。
- [ ] ユーザーが通しで遊び、手触り・見た目・物語について**2 回以上の感想と修正**を経て、了承している。
- [ ] 進行不能になる不具合がない。ボットの通しプレイが自動で完走する。
- [ ] ユーザーの PC で性能の目標（`40_技術設計.md` 7 章）を満たしている。
- [ ] **量産の手順書**（地域 1 つを作る手順：キット → 部屋 → 敵の派生 → イベント → 調整）が文書になっている。

## 5. ③ 量産

### 5.1 1 章ぶんの作業の流れ
1. **章の詳細設計**：部屋の構成、敵の派生、ボス、イベント、サブ依頼、会話の台本。
2. **Codex への発注**（1 章先行）：地域のキット、番機の派生、ボス、新しい人物、アーマー。
3. **制作**：地形 → 敵とボス → イベントと会話 → 音 → UI の追加。
4. **自動の確認**：データの検証、手触りの数値テスト、リプレイ、ボットの通しプレイ。
5. **ユーザーの試遊** → 修正。

### 5.2 各章の完了条件
- [ ] 章の最初から最後まで通しで遊べる。前の章のセーブから続けて遊べる。
- [ ] 章のメインが目標時間（`20_ゲームシステム設計.md` 23 章）に近い。
- [ ] ユーザーの試遊と修正を経ている。

### 5.3 並行して進めるもの
- 第2章の着手時に、第1章で見つかった改善を全体に反映する（企画段階で合意した「③ それを少し手直ししつつ後続を作っていく」）。
- 章をまたぐ要素（町の発展、賞金首、依頼の連続もの、図鑑）は、章ごとに少しずつ追加する。

## 6. ④ 仕上げ

| 分類 | 内容 |
|------|------|
| 調整 | 全体の難易度と経済のバランス、難易度別の調整 |
| 追加要素 | クリア後（深層アーカイブ、ボルタとの最後の競争、白磁の印、限界突破、エキスパート、強くてニューゲーム） |
| 品質 | 通しプレイの全体確認、性能、安定性、セーブデータの互換性 |
| 音 | 必要に応じて無料素材への差し替えとライセンスの記録 |
| 販売準備 | デスクトップアプリ化（Electron を第一候補）、ストアのページ（ユーザー）、**タイトルと名前の商標調査**、使用素材とフォントのライセンスの一覧 |
| 言語 | 日本語で発売。英語は文字列の表を翻訳して追加できる状態にしておく |

## 7. 試遊と感想の回し方

| 手段 | 内容 |
|------|------|
| 試遊版 | 変更のたびに試遊版を更新する（届け方は MVP で決定） |
| 調整パネル | 気になる数値をその場でいじり、「YAML としてコピー」で Claude に渡す |
| 入力の記録 | 不具合や違和感があった場面の入力を記録し、ファイルを渡してもらう。Claude が同じ状況を再現する |
| 感想の書き方 | 「どの場面で」「何をしたら」「どう感じたか」「どうなってほしいか」の 4 点があると、数値に落とし込みやすい |

## 8. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| 絵の一貫性（Codex が描く複数の向きの絵が食い違う） | 3D 化の精度が落ちる | 全方向を 1 枚のシートに描く指定、基準線、spec.md の色の数値。食い違いは修正指示で詰める |
| スクリプトで作る 3D モデルの品質 | 見た目の魅力が不足する | 画風を「スクリプトで作りやすい造形」に寄せる（アートバイブルの判断基準に含めた）。設定画と確認用の画像を並べて比べる工程を必ず通す |
| アニメーションの硬さ | 手触りと魅力が落ちる | メリハリのある動き、揺れものの物理計算、上半身と下半身の分離、試遊での重点確認 |
| 物量（メイン 16 時間） | 完成が遠のく | データ駆動、部品キットの再利用、章の型の標準化、ボットによる自動確認 |
| 手触りの調整 | 面白さの核が決まらない | 調整パネル、手触りの数値テスト、MVP の段階から試遊 |
| ブラウザの性能 | fps が落ちる | 性能の予算の管理、品質設定、インスタンス描画、ライトマップ |
| タイトルの重複 | 販売時に名前を変える必要が出る | 旧題『ワンダリング・アーク』は同名のゲームがあったため『アークウォーカー』に変更済み。ゲーム名の検索では同名なし。販売前に商標データベース（J-PlatPat、USPTO、EUIPO）で正式に調べる。ロゴは差し替えやすく作る |
| 名前の重複 | 印象の混同 | ヤーナ（『ユニコーンオーバーロード』に同名の魔女）、ボルタ（『おしりたんてい』に同名の脇役）。どちらも一般的な名前で役柄も違うため影響は小さいと判断するが、気になれば差し替える |
| 「町を背負って歩く巨大なもの」の先行作品 | 独自性が弱く見える | 『ゼノブレイド2』の巨神獣、『ONE PIECE』のゾウなど先行例がある。**生き物ではなく機械**であること、巡礼路とノード、盾と方舟という仕組みで差をつける。発注書でも似せないよう指定済み |
| 範囲の膨張 | 完成しない | 章ごとの完了条件を守る。追加のアイデアは「後で検討」の一覧に置き、段階の区切りで判断する |
