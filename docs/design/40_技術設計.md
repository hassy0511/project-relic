> プログラムの構成、データの持ち方、3D モデル・音の制作パイプライン、テストと検証の方法を定める。
> MVP の実装はこの文書に沿って始める。

## 1. コンテナでの検証結果（2026-09-27 実施）

| 確認したこと | 結果 |
|-------------|------|
| npm パッケージの取得 | three 0.186.1、@dimforge/rapier3d-compat 0.21.0、vite 8.3.1 を取得できる |
| Blender をスクリプトで動かせるか | **可**。PyPI の `bpy`（Blender 4.5.14 LTS、Python 3.11）で、骨入り・アニメーション付きのモデルを生成し、GLB に書き出せた（0.14 秒） |
| Blender で確認用の画像を描けるか | **Cycles（CPU）で可**（小さな画像で 0.7 秒）。EEVEE と Workbench は GPU 用のライブラリ（EGL）がないため使えないが、不要 |
| ブラウザで 3D を描いて撮影できるか | **可**。ヘッドレス Chromium（Playwright 1.56、ソフトウェア描画の WebGL2）で、Blender 製の GLB を three.js で読み込み、骨のアニメーションを再生して撮影できた |

→ **「Blender で作る → ゲームで動かす → 自動で撮影して確かめる」の一連の流れがコンテナ内で回ることを確認済み。**

注意：ヘッドレス環境の描画は CPU で行うため、fps はあてにならない。性能は描画回数やポリゴン数などの指標で管理し、実際の fps はユーザーの PC で確認する。

## 2. 技術スタック

| 分類 | 採用 | 理由 |
|------|------|------|
| 言語 | TypeScript（strict） | 型で大量のゲームコードとデータの整合性を守る |
| ビルド | Vite | 速い開発サーバーと静的ビルド |
| 描画 | Three.js（WebGL2） | 実績が多く、Claude が扱いやすい。将来 WebGPU に移る余地もある |
| 物理・当たり判定 | Rapier 3D（compat 版） | キャラクターコントローラー、レイキャスト、衝突判定。WASM が JS に埋め込まれていて配布が楽。Node.js でも動く |
| 3D 制作 | Blender 4.5 LTS（`bpy`、ヘッドレス） | モデル・骨・アニメーション・地形をすべて Python スクリプトで作る。スクリプトが正本になる |
| ゲームデータ | YAML ＋ zod による検証 | 敵・武器・会話・イベント・配置を、コードに触れずに編集できる |
| UI | HTML/CSS を画面に重ねる（DOM）。メニューは軽量ライブラリ（Preact）で組む | 文字がきれいで、画面数の多いメニューも作りやすい |
| 音 | Web Audio API。素材は Python の自作シンセで事前に書き出す | 後から無料素材に差し替えやすい |
| テスト | Vitest（単体・シミュレーション）、Playwright（ブラウザでの通し確認と撮影） | |
| デバッグ | lil-gui の調整パネル、独自の表示 | |
| 配布 | Web 版で開発 → 販売時にデスクトップアプリ化（Electron を第一候補） | Electron は全 OS で同じ Chromium を使うため、描画の差が出にくい |

## 3. 全体構成

### 3.1 層の分け方

```
┌───────────────────────────────────────────────┐
│ ui（HUD・メニュー。DOM）      audio（BGM・効果音）   │
├───────────────────────────────────────────────┤
│ view（描画：3D の見た目、アニメーション、エフェクト、カメラ） │
├───────────────────────────────────────────────┤
│ sim（ゲームの中身：移動、戦闘、AI、物語、所持品…）       │
│   └ physics（Rapier の包み）                         │
├───────────────────────────────────────────────┤
│ core（ループ、時間、イベント、乱数）  platform（入力、保存） │
│ content（データの読み込みと検証）                       │
└───────────────────────────────────────────────┘
```

**最重要の原則：ゲームの中身（sim）は描画（view）に依存しない。**
- sim は画面がなくても Node.js 上で動く。
- これにより、次のことができる。
  - 描画なしで高速にゲームを進めるテスト（ジャンプの高さ、ボスの段階遷移など）
  - 入力の記録と再生（リプレイ）によるバグの再現と回帰テスト
  - ボットによる第1章の自動通しプレイ
- sim は three.js の数学クラス（Vector3 など）は使ってよいが、描画のオブジェクトには触れない。view は毎フレーム sim の状態を読んで見た目を合わせる。

### 3.2 ゲームループ
| 項目 | 仕様 |
|------|------|
| 更新の刻み | ゲームの中身は **60Hz の固定刻み**で進める。描画は画面の更新に合わせ、前後の状態を補間する |
| 取りこぼし | 1 フレームで最大 5 刻みまで進める（それ以上は切り捨ててゆっくり進む） |
| ヒットストップ | 攻撃した側とされた側だけ、個別に時間を止める |
| 見切りのスロー | 全体の時間の進みを遅くする |
| 乱数 | 種つきの乱数だけを使う（sim 内で `Math.random` は禁止）。同じ入力なら同じ結果になる |

### 3.3 エンティティの作り
- 軽量なエンティティ＋コンポーネント方式。エンティティは「位置」「HP」「AI」などの部品を必要なものだけ持つ。システムが部品の組み合わせで対象を絞って毎刻み処理する。
- 敵の行動は型ごとの**状態機械クラス**で書き、数値は YAML から読む。
- 弾は物理の剛体にせず、プールした軽量オブジェクトを毎刻みレイキャストで進める（高速でもすり抜けない）。

### 3.4 当たり判定のレイヤー
| レイヤー | 例 | ぶつかる相手 |
|---------|-----|-------------|
| 地形 | 床、壁 | すべて |
| プレイヤー | ハル | 地形、敵、敵の弾、トリガー、拾える物 |
| 敵 | 番機 | 地形、プレイヤー、プレイヤーの弾、ほかの敵 |
| プレイヤーの弾 | 主武器の弾 | 地形、敵、壊せる物 |
| 敵の弾 | | 地形、プレイヤー |
| 攻撃判定 | 光刃、体当たり | 被弾判定とだけ重なりを調べる（押し合いはしない） |
| トリガー | イベントの範囲 | プレイヤー |
| 拾える物 | セル | プレイヤー |
| カメラ | | 地形だけ |

- 攻撃は、判定の形と被弾判定の重なりを毎刻み調べる。同じ攻撃が同じ相手に何度も当たらないよう、攻撃ごとに「当てた相手」を記録する。

### 3.5 プレイヤーの動き
- Rapier のキャラクターコントローラー（カプセル型）を使う。段差の自動乗り越え 0.35m、地面への吸着 0.3m、登れる坂 45°。
- 速度の計算（重力、ジャンプ、ダッシュ、空中制御）は自前で行い、コントローラーには「動きたい量」だけを渡す。操作感を数値で細かく調整するため。

### 3.6 アニメーション
- three.js の AnimationMixer に、状態機械をかぶせて使う。
  - 移動：待機・歩き・走りを速さで混ぜる
  - ジャンプ：踏み切り・上昇・下降・着地
  - 攻撃：クリップごとに「当たり判定が出ている時間」をデータで定義する
- **上半身と下半身を分ける**。走りながら撃つため、上半身だけ射撃のポーズを重ね、背骨と腕をロックオン対象の方向へ回す。
- ルートモーション（アニメーションが位置を動かす方式）は使わない。位置はすべてコードで動かし、操作の正確さを優先する。

### 3.7 エリアの読み込み
- 1 エリア＝地形の GLB（見た目、当たり判定用の簡易メッシュ、名前つきの目印）＋配置の YAML。
- エリアの間は扉やエレベーターで区切り、短い暗転で切り替える。読み込みは 3 秒以内を目標にする。
- 当たり判定用のメッシュは、Blender 上で名前の末尾を `_col` にしたものを使う。
- 同じ部品の繰り返しは、インスタンス描画で描画の回数を抑える。

### 3.8 セーブデータ
- JSON。先頭に形式の版番号を持ち、版が変わったときは変換処理で古いデータを読めるようにする。
- 保存先：Web 版はブラウザのローカルストレージ、デスクトップ版はファイル。
- 中身：

| 区分 | 内容 |
|------|------|
| 概要 | プレイ時間、章、保存日時 |
| 物語 | フラグ、依頼の状態 |
| 成長 | 所持品、強化の段階、チップ、アーマー、剣技 |
| 収集 | 収集物の取得状況（ID ごと） |
| 世界 | エリアごとの状態（開けた宝箱、壊した壁、開けた扉） |
| プレイヤー | いる場所、HP |

設定（操作の割り当て、音量など）はセーブ枠とは別に保存する。

## 4. ゲームデータの形式

### 4.1 置き場所
```
content/
  enemies/        敵の型ごとの数値と行動の設定
  bosses/
  weapons/        主武器の曲線、費用、チップ
  special/        特殊武器
  armor/
  items/
  shops/
  quests/
  dialogue/ch1/   会話
  events/ch1/     イベントの台本
  areas/          エリアごとの配置
  strings/ja.yaml UI の文言
  audio.yaml      音の ID と素材ファイルの対応
```

### 4.2 例：敵
```yaml
id: enemy.sentry
archetype: sentry
model: models/enemy_sentry.glb
perception: { view_angle: 120, sight: 18, hearing: 12 }
by_chapter:
  1: { hp: 40, shot_damage: 8 }
  2: { hp: 54, shot_damage: 11 }
behavior:
  keep_distance: [8, 14]
  burst: { count: 3, interval: 0.2, windup: 0.5 }
poise: 20
drops: { cells: [5, 12], weapon_energy_chance: 0.15 }
```

### 4.3 例：会話
```yaml
id: ch1.yana_gate
lines:
  - { who: yana, face: serious, text: "行くんだろ。止めたって聞きやしないんだから。" }
  - { who: haru, face: determined, text: "……ごめん、ヤーナ。" }
  - { action: give_item, item: weapon.spark }
  - { who: yana, face: smile, text: "回収屋は、持ち帰るまでが仕事だよ。あんたの親父の口ぐせさ。" }
```

### 4.4 例：イベントの台本
```yaml
id: ch1.frame_fitting
steps:
  - letterbox: on
  - camera: { shot: seal_room_wide, duration: 2.0 }
  - anim: { actor: haru, clip: look_around }
  - sfx: seal_unlock
  - parallel:
      - camera: { shot: frame_closeup, duration: 3.0, ease: in_out }
      - vfx: { name: frame_assemble, at: marker.frame_pedestal }
  - say: ch1.nagomi_boot
  - flag: ch1.frame_fitted
  - letterbox: off
```

### 4.5 検証
- すべての YAML を、起動時とビルド時に zod のスキーマで検証する。
- 参照の整合性（存在しない敵 ID、地形にない目印、未定義の文言 ID など）もビルド時に検査する。
- 会話の 1 行の長さの上限（会話ウィンドウに収まるか）も検査する。

## 5. 3D モデルとアニメーションの制作パイプライン

### 5.1 流れ
```
Codex の設定画（art/concepts/）
      ↓ Claude が読み取り、比率・色・部品を把握
Blender の Python スクリプト（tools/blender/models/*.py）
      ↓ npm run assets
GLB（public/assets/models/）＋ 確認用の画像（art/renders/）
      ↓
設定画と確認用の画像を並べて比べる → スクリプトを修正（繰り返す）
      ↓
ゲーム内で表示・撮影して最終確認
```

### 5.2 スクリプトの構成
| 場所 | 内容 |
|------|------|
| `tools/blender/lib/` | 共通の道具：形の生成（押し出し、面取り、左右対称、ブーリアン）、UV、頂点カラー、材質、**標準の人型の骨**、アニメーションのキーフレーム補助、GLB の書き出し設定、確認用の撮影（正面・側面・背面・斜め） |
| `tools/blender/models/` | モデル 1 つにつきスクリプト 1 つ |
| `tools/blender/anims/humanoid/` | 人型の共通アニメーション（待機、走り、ジャンプ、ダッシュ、射撃、光刃のコンボなど） |
| `tools/blender/levels/` | 部屋ごとに、部品キットを組み立てるスクリプト |
| `tools/blender/build.py` | 変更のあったスクリプトだけを実行して書き出す（内容のハッシュで判定） |

### 5.3 方針
- **人型はすべて同じ骨の構成**にして、アニメーションを使い回す（主要キャラは個別の動きを追加）。
- 表情は、目と口のテクスチャの差し替え方式を第一候補にする（アニメ調と相性がよく、軽い）。アートバイブルの画風で最終決定する。
- 揺れもの（スカーフ、コートの裾、髪）は、ゲーム中のバネの計算で動かす。手付けのアニメーションの硬さを補う。
- 確認用の撮影は、設定画の三面図と**同じ縮尺・同じ向き**で行い、並べて比較する。

### 5.4 ポリゴン数などの目安（アートバイブル確定後に見直す）
| 対象 | 三角形の数 | テクスチャ |
|------|-----------|-----------|
| 主要キャラ | 6,000〜10,000 | 1024² ×1 程度（頂点カラーとの併用） |
| 町の住人 | 3,000〜5,000 | 512² |
| 小型の敵 | 2,000〜4,000 | 512² |
| ボス | 15,000〜30,000 | 2048² |
| 地形の部品 | 50〜500 | 地域ごとに共有のテクスチャ |

### 5.5 アニメーションの本数の見込み
| 対象 | 本数 |
|------|------|
| ハル | 約 60 |
| 人型の共通（住人・幹部） | 約 15＋個別 |
| 小型の敵 | 8〜15 ずつ |
| ボス | 20〜30 ずつ |

## 6. 音の制作パイプライン

| 項目 | 方針 |
|------|------|
| 作り方 | `tools/audio/` に Python の自作シンセ（発振器、エンベロープ、フィルター、FM、ノイズ、リバーブ、ディレイ）を置く。曲はテキストの楽譜データ、効果音は YAML の数値で定義し、事前に書き出す |
| 形式 | OGG（Vorbis）。エンコード手段は MVP で確定する |
| 再生 | BGM はループ位置つき。探索と戦闘で楽器の重なりを切り替える。効果音は 3D 定位。しゃべり音は再生時に合成する |
| 差し替え | すべての音は `content/audio.yaml` の ID で参照する。無料素材に差し替えるときはファイルと対応表だけを変える。使用した素材のライセンスは `docs/licenses.md` に記録する |

## 7. 描画

| 項目 | 方針 |
|------|------|
| 画風 | アートバイブルで決める（トゥーン寄り／PS1 風ローポリ寄りなど）。どちらにも対応できるよう、材質は自前のシェーダーを 1 系統に集約する |
| 地形の照明 | Blender の Cycles で焼き込んだライトマップ＋動く光（候補。アートバイブル確定後に決定） |
| 影 | 平行光源の影。屋内 1 段、屋外 2〜3 段のカスケード |
| 後処理 | 光のにじみ（ブルーム）、色調補正、アンチエイリアス |
| 品質設定 | 低・中・高（解像度の倍率、影、後処理） |

### 性能の目標
| 項目 | 目標 |
|------|------|
| fps | GTX 1060 級の PC で 1080p・60fps。内蔵 GPU（Iris Xe 級）で 720p・30fps 以上 |
| 描画の回数 | 1 フレーム 300 回未満 |
| 画面内の三角形 | 60 万未満 |
| テクスチャのメモリ | 300MB 未満 |
| エリアの読み込み | 3 秒以内 |
| JS のメモリ | 400MB 未満 |

## 8. テストと検証

| 種類 | 内容 | 実行のタイミング |
|------|------|-----------------|
| 単体テスト | ダメージ計算、強化の曲線、経済、セーブの変換、フラグ条件、会話の読み込み、ロックオンの対象選び | 変更のたび |
| **手触りの数値テスト** | 描画なしのシミュレーションで、ジャンプの最高点 2.2m、ダッシュ距離 3.3m、1.8m の段に届き 2.4m には届かない、などを確かめる。**調整した手触りが知らないうちに壊れるのを防ぐ** | 変更のたび |
| データの検証 | YAML のスキーマ、参照の整合性、文言の長さ | 変更のたび |
| リプレイテスト | 記録した入力を再生し、落ちずに所定の地点まで進めるかを確かめる。ユーザーの試遊の記録も使う | 変更のたび |
| ボットの通しプレイ | 決められた道順と簡単な戦闘ロジックで、第1章を最初から最後まで自動で遊ぶ | 1 日 1 回程度 |
| ブラウザでの確認 | 起動 → タイトル → ニューゲーム → 各エリアの読み込み → 撮影。コンソールのエラーがないこと、画面が真っ黒でないことを確かめる。撮影した画像は Claude が目視で確認する | 変更のたび |

- GitHub Actions で、型チェック、Lint、単体テスト、シミュレーション、データの検証、ビルド、ブラウザでの確認を自動実行する。

## 9. デバッグ機能（開発版のみ）

| 機能 | 用途 |
|------|------|
| **調整パネル** | 移動・カメラ・ロックオン・武器の数値をゲーム中にその場で変えられる。**「YAML としてコピー」ボタン**で、ユーザーが調整した値をそのまま Claude に渡せる |
| 入力の記録 | 試遊中の入力を記録してファイルに保存する。不具合の報告に添えてもらえば、Claude が同じ状況を再現できる |
| 自由カメラ、目印へのワープ | 地形の確認 |
| フラグの編集、アイテムの付与、無敵、時間の速さ | 途中の場面の確認 |
| 当たり判定と AI の状態の表示 | 戦闘の調整 |
| 性能の表示 | fps、描画の回数、三角形の数 |

## 10. 試遊版の届け方（MVP で決める）

| 候補 | 長所 | 短所 |
|------|------|------|

## 11. ディレクトリ構成

```
/
├─ docs/                 企画・設計・発注書
├─ art/
│   ├─ concepts/         Codex から納品された設定画
│   └─ renders/          モデルの確認用画像（自動生成）
├─ content/              ゲームデータ（YAML）
├─ src/
│   ├─ core/             ループ、時間、イベント、乱数
│   ├─ platform/         入力、保存、ウィンドウ
│   ├─ physics/          Rapier の包み
│   ├─ sim/              ゲームの中身（player, enemies, combat, ai, weapons, world, story, economy）
│   ├─ view/             描画（renderer, materials, animation, vfx, camera）
│   ├─ ui/               HUD、メニュー
│   ├─ audio/            再生エンジン
│   ├─ content/          データの読み込みと検証
│   └─ debug/            デバッグ機能
├─ tools/
│   ├─ blender/          モデル・アニメーション・地形のスクリプト
│   └─ audio/            シンセと楽譜
├─ public/assets/        生成された GLB・音（リポジトリに含める）
└─ tests/                unit/、sim/、e2e/
```

- 生成物（GLB、音）はリポジトリに含める。CI で Blender を動かさずに済み、試遊版をすぐ作れるため。正本はあくまでスクリプト。

## 12. コードの約束事

- TypeScript の strict モード。ESLint と Prettier で書式をそろえる。
- 単位はメートルと秒。角度は内部ではラジアン、データでは度。
- ID は `enemy.sentry`、`ch1.frame_fitted` のようにドット区切りの小文字。ファイル名はケバブケース。
- sim の中では `Math.random`、`Date.now`、描画のオブジェクトを使わない。
- 依存するライブラリは MIT／Apache などの商用利用できるライセンスに限る。フォントも商用利用できるもの（OFL など）に限る。
